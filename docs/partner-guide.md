# dbt-agents-schema partner guide

This guide covers dbt-agents-schema 0.1.0 (spec v1). It is for teams that publish dbt
project metadata so AI agents can use it.

## What it does

`dbt-agents-schema` reads a dbt project's `target/manifest.json` and its markdown skill
files, then writes them into an **agents schema** in your warehouse: `ROOT`,
`DBT_PROJECT`, `DBT_MODEL`, `DBT_COLUMN`, `DBT_DEPENDENCY` and `SKILL_USE`. Agents
query those tables with plain SQL to find models, columns, lineage and skills.

Every row has a `project` key. Each publish replaces **only its own project's rows**, so
any number of dbt projects (finance, marketing, ...) can share one agents schema. The
table and column names match the dbt Labs `agents_schema` tool, so existing agents and
its analyst skill keep working. They just see every project.

- Warehouses: Snowflake, BigQuery, Databricks. DuckDB works for local use and demos.
- dbt runtimes: dbt v1 (dbt-core), dbt v2 (Fusion) and dbt platform. The tool reads
  only `manifest.json`.
- CI: a reusable GitHub Actions workflow and a GitLab CI template. Both are thin
  wrappers around the CLI.
- A built-in analyst skill (`skill/dbt-agents-schema-analyst` in `ROOT`) teaches agents
  how to query the schema in your warehouse's SQL dialect.

A publish goes: load config and manifest, check, plan, connect, ensure tables, ownership
guard, swap, report. On Snowflake, BigQuery and DuckDB the swap runs in one transaction.
On Databricks each table is replaced with one atomic `INSERT INTO ... REPLACE WHERE`
statement. A failed publish on Snowflake, BigQuery or DuckDB leaves the previous rows in
place. On Databricks some tables may already hold the new rows; publishing again
completes the swap.

## Install

Python 3.11 or later. Install the extra for your warehouse:

```bash
pip install "dbt-agents-schema[snowflake]==0.1.0"   # or [bigquery], [databricks], [duckdb]
dbt-agents-schema --version
```

If your organisation installs from git rather than a package index:

```bash
pip install "dbt-agents-schema[snowflake] @ git+https://github.com/DavidHrncir/dbt-agents-schema@v0.1.0"
```

If the extra is missing, the CLI exits 2 and prints the `pip install` command to run.
The command is `dbt-agents-schema`. It does not clash with the dbt Labs `agents-schema`
command, so both can be installed side by side.

To set up a project, run this in the dbt project root (next to `dbt_project.yml`):

```bash
dbt-agents-schema init --ci github     # or --ci gitlab, or --ci none
```

`init` writes `agents_schema.yml`, `agents/skills/example.md` and the CI caller file,
and prints a `.pre-commit-config.yaml` snippet. It never overwrites a file unless you
pass `--force`.

## Configuration reference

`agents_schema.yml` lives in the dbt project root. Pass `--config` to use another path.
Unknown keys are an error. If the file is absent every key takes its default, and
`check` reports `config_missing`.

```yaml
version: 1
project: finance
owner: data-platform@acme.com
description: Finance marts
include_packages: true
exclude_packages: []
skills_dir: agents/skills
environments:
  prod:
    credentials: env
    database: ANALYTICS
    schema: AGENTS
  dev:
    credentials: dbt_profile
    schema: "{{ target_schema }}_AGENTS"
check:
  description_scope: public
  external_schemas: []
  rules:
    config_missing: warning
    missing_model_description: warning
    missing_column_description: warning
    sampled_values_in_description: error
    skill_without_uses: warning
    skill_unresolved_uses: error
```

The table below is generated from the JSON Schema shipped in the package. Do not edit
it by hand. Run `uv run python scripts/gen_config_reference.py` instead; `make verify`
fails when it is stale.

**Templates.** `schema` and `database` accept `{{ target_schema }}`,
`{{ target_database }}`, `{{ project }}` and `{{ env }}`. Any other `{{ ... }}` is a
config error. `target_schema` and `target_database` come from your dbt profile, so they
only work with `credentials: dbt_profile`. On Snowflake, rendered values are uppercased.

**Credentials: `env`.** Reads `WAREHOUSE_CREDENTIALS`, a YAML or JSON mapping. The
shapes are the same as the dbt Labs tool, so existing CI secrets carry over:

| Warehouse | Keys |
| --- | --- |
| Snowflake | `type: snowflake`, `account`, `user`, `warehouse`, `database`, optional `role`; one of `password`, `private_key_pem` (+ optional `private_key_passphrase`), `private_key_path` |
| BigQuery | `type: bigquery`, `project_id`, optional `location`; `credentials_json` (service-account mapping) or `auth_method: adc` |
| Databricks | `type: databricks`, `host`, `http_path`, `catalog`, `token` |
| DuckDB | `type: duckdb`, `path` |

`write-parse-profile` also needs the dbt target schema, so add `schema` (BigQuery:
`dataset`) to `WAREHOUSE_CREDENTIALS`, or provide `DBT_PROFILES_YML` instead. Publish
ignores this key.

**Credentials: `dbt_profile`.** Reads the profile named in `dbt_project.yml` from
`profiles.yml`. The file is found through `--profiles-dir`, then `DBT_PROFILES_DIR`, then
the project directory, then `~/.dbt/`. The target is `--target`, else the profile's
default. Inside `profiles.yml` only `{{ env_var('NAME') }}` and
`{{ env_var('NAME', 'default') }}` are supported. Supported adapters: snowflake
(password, key pair, `authenticator: externalbrowser`), bigquery (`oauth`,
`service-account`, `service-account-json`), databricks (token) and duckdb.

**Skills.** Every `*.md` file under `skills_dir` is published as
`skill/<project>/<path>`. Front matter declares what the skill reads, and `check`
verifies it:

```markdown
---
uses:
  schemas: [FINANCE_MARTS]
  tables: [FINANCE_MARTS.FCT_REVENUE]
---
# Revenue skill
```

## CLI reference

These options work with every command: `--project-dir` (default `.`), `--config`
(default `<project-dir>/agents_schema.yml`), `--manifest` (default
`<project-dir>/target/manifest.json`). `dbt-agents-schema --version` prints the version.

| Command | Options | What it does |
| --- | --- | --- |
| `dbt-agents-schema check` | `--parse`, `--format text\|json\|github\|gitlab`, `--output` | Validates config, manifest and skills. Needs no warehouse. `--parse` runs `dbt parse` first. `github` prints PR annotations; `gitlab` writes a Code Quality report to `--output` (default `gl-code-quality-report.json`) and prints text. |
| `dbt-agents-schema publish` | `--env`, `--target`, `--profiles-dir`, `--dry-run`, `--force-takeover` | Checks, plans and replaces this project's rows in the agents schema for environment `--env`. `--dry-run` prints the plan and target schema without connecting. `--force-takeover` overrides the ownership guard (exit 4). |
| `dbt-agents-schema unpublish` | `--env`, `--target`, `--profiles-dir`, `--project`, `--yes` | Deletes one project's rows, including its `ROOT` rows. `--project` defaults to this project's key. Without `--yes` it asks for confirmation, and refuses when stdin is not a terminal. |
| `dbt-agents-schema init` | `--ci github\|gitlab\|none`, `--force` | Writes starter files (see [Install](#install)). |
| `dbt-agents-schema fetch-manifest` | `--account-id`, `--job-id`, `--host`, `--out` | Downloads the latest `manifest.json` of a dbt platform job (see [dbt platform projects](#dbt-platform-projects)). |
| `dbt-agents-schema write-parse-profile` | `--out` | Writes `<out>/profiles.yml` from `WAREHOUSE_CREDENTIALS` so CI can run `dbt parse`. The file holds no secrets. |

`--target` and `--profiles-dir` only apply to environments with
`credentials: dbt_profile`.

## GitHub setup

1. Add the repository secret `WAREHOUSE_CREDENTIALS` (Settings > Secrets and variables >
   Actions). Optionally add `DBT_PROFILES_YML`, the `profiles.yml` that `dbt parse`
   should use. Without it, the workflow runs `write-parse-profile`.
2. Copy `examples/github/agents-schema.yml` to `.github/workflows/agents-schema.yml`
   (`init --ci github` does this for you). It checks every pull request and publishes on
   push to `main`:

```yaml
jobs:
  check:
    if: github.event_name == 'pull_request'
    uses: DavidHrncir/dbt-agents-schema/.github/workflows/dbt-agents-schema.yml@v0.1.0
    with:
      mode: check
      package-version: "0.1.0"
      dbt-adapter: dbt-snowflake
    secrets:
      WAREHOUSE_CREDENTIALS: ${{ secrets.WAREHOUSE_CREDENTIALS }}
      DBT_PROFILES_YML: ${{ secrets.DBT_PROFILES_YML }}
  publish:
    if: github.event_name == 'push'
    concurrency:
      group: dbt-agents-schema-${{ github.repository }}
      cancel-in-progress: false
    uses: DavidHrncir/dbt-agents-schema/.github/workflows/dbt-agents-schema.yml@v0.1.0
    with:
      mode: publish
      package-version: "0.1.0"
      dbt-adapter: dbt-snowflake
      environment: prod
    secrets:
      WAREHOUSE_CREDENTIALS: ${{ secrets.WAREHOUSE_CREDENTIALS }}
      DBT_PROFILES_YML: ${{ secrets.DBT_PROFILES_YML }}
```

Workflow inputs: `project-dir` (default `.`), `package-version` (required),
`python-version` (default `3.12`), `dbt-adapter` (required), `dbt-version` (default
`>=1.8,<2`), `mode` (`check` or `publish`), `environment` (default `prod`). Pin
`uses:` to a release tag and set `package-version` to the same release. In check mode,
findings show up as annotations on the pull request. Secrets go only to the steps that
need them, never to `pip`, `dbt deps` or `dbt parse`.

If the dbt project lives in a subdirectory, set `project-dir`. For a monorepo with
several dbt projects, add one `check` and one `publish` job per project. Give each its
own `project-dir` and its own `concurrency` group.

## GitLab setup

1. Add the CI/CD variable `WAREHOUSE_CREDENTIALS` (Settings > CI/CD > Variables). Make
   it type **File** and **protected**, so only default-branch pipelines receive it.
   GitLab cannot mask a multi-line JSON or YAML document, so don't rely on masking.
2. For merge request checks, also set an unprotected `DBT_PROFILES_YML`. Use the output
   of `dbt-agents-schema write-parse-profile`, which holds no secrets.
3. Include the template from your `.gitlab-ci.yml` (see `examples/gitlab/.gitlab-ci.yml`;
   `init --ci gitlab` writes it):

```yaml
include:
  - remote: https://raw.githubusercontent.com/DavidHrncir/dbt-agents-schema/v0.1.0/templates/gitlab/dbt-agents-schema.yml
    inputs:
      package_version: "0.1.0"
      dbt_adapter: dbt-snowflake
      environment: prod
```

You can also use `include: project:` with `ref: v0.1.0` and
`file: templates/gitlab/dbt-agents-schema.yml`, or copy the template into your repository
and use `include: local:`. The template does not use the GitLab CI/CD Catalog.

Inputs: `project_dir`, `package_version`, `python_version`, `dbt_adapter`,
`dbt_version`, `mode` (`auto` (default), `check` or `publish`), `environment`. With
`mode: auto` there are two jobs. `dbt-agents-schema-check` runs on merge request
pipelines and its findings appear in the Code Quality widget.
`dbt-agents-schema-publish` runs on the default branch, and
`resource_group: dbt-agents-schema-$CI_PROJECT_PATH` makes sure only one publish runs
at a time.

**Pre-commit.** To run `check --parse` locally before each commit:

```yaml
repos:
  - repo: https://github.com/DavidHrncir/dbt-agents-schema
    rev: v0.1.0
    hooks:
      - id: dbt-agents-schema-check
        additional_dependencies: ["dbt-core>=1.8,<2", "dbt-snowflake"]
```

## Developer workflow

Developers publish to their own schema with the `dev` environment. It uses their
existing dbt profile, so they need no new secret:

```bash
dbt parse
dbt-agents-schema check
dbt-agents-schema publish --env dev --dry-run      # see what would be written, no connection
dbt-agents-schema publish --env dev                # writes to <your target schema>_AGENTS
dbt-agents-schema publish --env dev --target ci --profiles-dir ./profiles
dbt-agents-schema unpublish --env dev --yes        # clean up
```

The default `dev` schema is `{{ target_schema }}_AGENTS`. Each developer gets their own
agents schema, and `prod` is never touched. To point an agent at your dev schema, give it
the `ROOT` table in that schema.

## dbt platform projects

If dbt platform builds your project, download its manifest instead of running
`dbt parse`:

```bash
export DBT_CLOUD_API_TOKEN=...            # service token with job read access
dbt-agents-schema fetch-manifest --account-id 12345 --job-id 67890
dbt-agents-schema publish --env prod
```

`fetch-manifest` calls the Administrative API v2 endpoint
`/api/v2/accounts/<account_id>/jobs/<job_id>/artifacts/manifest.json`. It gets the
manifest from the latest run of that job. `--host` defaults to `cloud.getdbt.com`. For
other regions or cells, pass your access URL host, for example
`--host ab123.us1.dbt.com`. `--out` defaults to `<project-dir>/target/manifest.json`,
where `check` and `publish` look for it. If the download fails, any existing manifest is
kept. The token is never logged and is not sent along when a redirect points to another
host.

Choose a job that runs on your production environment and generates docs or runs
`dbt build`, so the manifest matches what is deployed.

## Migrating from the dbt Labs tool

1. **Credentials.** Keep your `WAREHOUSE_CREDENTIALS` secret. The shapes are identical.
2. **Config.** Run `dbt-agents-schema init`, set `project` (defaults to the dbt project
   name) and point the `prod` environment at your existing agents schema.
3. **Skills.** Keep your skill files in `agents/skills/`. The front matter convention
   (`uses.schemas`, `uses.tables`) is the same. Run `dbt-agents-schema check`. It now
   fails on `uses` entries that match no published model (`skill_unresolved_uses`). Add
   schemas dbt does not build to `check.external_schemas`.
4. **First publish.** The first publish migrates the tables in place. It runs
   `ALTER TABLE ... ADD COLUMN` for the new columns (`project`, `package_name`, `alias`,
   ...) and creates `DBT_PROJECT`. It never drops a table or column. Rows the dbt Labs
   tool wrote have `project IS NULL`. They are removed on the first publish, and the
   report shows how many. Each project then re-publishes its own rows.
5. **Switch every project.** Once a schema is migrated, stop running the dbt Labs tool
   against it. That tool recreates the tables, which drops the new columns and every
   other project's rows. Remove its CI job in the same change that adds this one.
6. **Agents.** No change needed. The `ROOT` keys `overview`, `model`, `column`,
   `dependency` and `skill_use` are still present. To see one project only, agents can
   filter on `project`. The built-in analyst skill shows how.

## Warehouse permissions

The publishing identity creates the schema if it does not exist, creates and alters the
six tables, and deletes and inserts rows. If you create the schema up front, you can drop
the schema-creation privilege. Grant read access (SELECT) to the agents.

**Snowflake** (role in `WAREHOUSE_CREDENTIALS` or the profile):

```sql
GRANT USAGE ON WAREHOUSE <wh> TO ROLE <publisher>;
GRANT USAGE ON DATABASE <db> TO ROLE <publisher>;
GRANT CREATE SCHEMA ON DATABASE <db> TO ROLE <publisher>;   -- or create AGENTS yourself and:
GRANT USAGE, CREATE TABLE ON SCHEMA <db>.AGENTS TO ROLE <publisher>;
GRANT SELECT, INSERT, DELETE ON ALL TABLES IN SCHEMA <db>.AGENTS TO ROLE <publisher>;
GRANT SELECT, INSERT, DELETE ON FUTURE TABLES IN SCHEMA <db>.AGENTS TO ROLE <publisher>;
```

`ALTER TABLE ... ADD COLUMN` requires ownership of the table. When migrating tables the
dbt Labs tool created, publish once with the role that owns them, or transfer ownership
first.

**BigQuery** (service account or ADC identity):

- `roles/bigquery.jobUser` on the project that runs the queries.
- `roles/bigquery.dataEditor` on the agents dataset (create, alter, insert, delete, and
  the short-lived staging tables used for large tables).
- `bigquery.datasets.create` on the project only if the dataset does not exist yet.

**Databricks** (Unity Catalog; principal that owns the token):

```sql
GRANT USE CATALOG ON CATALOG <catalog> TO `<publisher>`;
GRANT CREATE SCHEMA ON CATALOG <catalog> TO `<publisher>`;  -- or create the schema and:
GRANT USE SCHEMA, CREATE TABLE ON SCHEMA <catalog>.agents TO `<publisher>`;
GRANT SELECT, MODIFY ON SCHEMA <catalog>.agents TO `<publisher>`;
```

Unity Catalog is required (the grants and `REPLACE WHERE` assume it). The SQL warehouse
also needs `CAN USE`. Publish stages rows in tables named `_DBT_AGENTS_SCHEMA_STAGE_*` in
the agents schema and drops them afterwards, also on failure. If the process is killed
mid-publish, drop any leftover `_DBT_AGENTS_SCHEMA_STAGE_*` tables by hand. Adding
columns to migrated tables requires ownership (or `MANAGE`) of those tables.

**DuckDB:** write access to the database file.

## Troubleshooting

Every error names the file, key or object involved and how to fix it. Look up the exit
code below.

### Exit 0 — success

Publish prints rows written per table, legacy rows removed, the target schema and the
elapsed time. `check` may still print warnings and info lines.

### Exit 1 — check errors

`check` or `publish` found at least one error-severity finding. Publish stops before it
connects. Common causes:

- `sampled_values_in_description`: a description contains profiling output (for example
  `min: 0`, `12% null`, `1,000 rows`). Rewrite it as prose, or set the rule to `warning`.
- `skill_unresolved_uses`: a skill's `uses` names a schema or table that no published
  model has. Fix the name, or list the schema in `check.external_schemas`.
- `skill_key_duplicate`, `skill_frontmatter_invalid`, `config_invalid`,
  `project_key_invalid`: fix the named file. These cannot be turned off. (`publish`
  reports an invalid or unparseable `agents_schema.yml` with exit 2, not 1.)

Run `dbt-agents-schema check --format json` for machine-readable output.

### Exit 2 — config, manifest or credential error

- Invalid `agents_schema.yml` (publish and unpublish), or an `unpublish --project` key
  that does not match the project pattern.
- `manifest_missing`: run `dbt parse` (or `fetch-manifest`) first, or pass `--manifest`.
- Unknown environment: `--env` must name an entry under `environments`.
- `WAREHOUSE_CREDENTIALS` not set, not a mapping, or missing a key. The message names
  the key.
- `target_schema` used with `credentials: env`. Use `dbt_profile`, or write the schema
  out in full.
- Missing extra: install `dbt-agents-schema[<warehouse>]`.
- The schema holds `DBT_PROJECT` rows with a newer `spec_version` than this tool.
  Upgrade dbt-agents-schema.
- `fetch-manifest`: `DBT_CLOUD_API_TOKEN` missing or rejected (401/403), or the job or
  run was not found (404).

### Exit 3 — warehouse or remote error

The warehouse rejected a statement or the connection failed. On Snowflake, BigQuery and
DuckDB no project rows were changed, though a new schema, table or column may already
have been created. On Databricks, tables replaced before the failure hold the new rows;
publish again once the cause is fixed. Check
the permissions above, the network, and that the warehouse is running. For
`fetch-manifest`, the dbt platform API returned an unexpected status, a network error,
or a response that is not a manifest.

### Exit 4 — ownership conflict

`DBT_PROJECT` already holds this `project` key, published from a different repository
(`repo_url`). Two repositories are using the same key. Give one of them a different
`project` in `agents_schema.yml`. If the project really has moved, run publish once with
`--force-takeover`.

### Other problems

- **Lineage queries are slow on very large DAGs.** The analyst skill's recursive
  queries stop at depth 20. DAGs with many diamonds can produce many paths, so filter
  on `project`, or lower the depth.
- **Another project's rows disappeared.** Someone ran the dbt Labs tool against the
  schema. Re-publish every project. See
  [Migrating from the dbt Labs tool](#migrating-from-the-dbt-labs-tool).
- **Databricks `ConcurrentAppendException` in logs.** Two publishes collided. The swap
  is retried automatically. Serialise publishes with `concurrency` or `resource_group`.
